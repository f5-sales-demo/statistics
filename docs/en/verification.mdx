Use the existing demo and complete [shared cURL setup](../setup/) first. For a new deployment, use the [Terraform reference](../deployment/). Keep the timer enabled after acceptance.

**1. Wait for both Azure VMs to finish application provisioning.**

**2. Resolve the demo hostname.**

```bash
dig +short "$XCSH_DEMO_HOST" A
```

**3. Check the public HTTPS health route and certificate.**

```bash
curl --silent --show-error --fail-with-body --output /dev/null \
  --write-out 'status=%{http_code} tls=%{ssl_verify_result}\n' \
  "https://$XCSH_DEMO_HOST/health"
```

Expect `status=200 tls=0`. Do not use `-k`.

**4. Check an API route through the load balancer.**

```bash
curl --silent --show-error --fail-with-body --output /dev/null \
  --write-out 'status=%{http_code}\n' \
  "https://$XCSH_DEMO_HOST/httpbin/get?statistics_probe=$(date -u +%s)"
```

**5. Send one authorized WAF probe to this F5-owned demo.**

```bash
XCSH_WAF_BODY="$(mktemp)"
trap 'rm -f "$XCSH_WAF_BODY"' EXIT
curl --silent --show-error --output "$XCSH_WAF_BODY" --write-out 'status=%{http_code}\n' \
  --get --data-urlencode "q=' OR 1=1--" \
  "https://$XCSH_DEMO_HOST/httpbin/get"
```

**6. Confirm the rejection page.**

```bash
grep -i '<title>Request Rejected</title>' "$XCSH_WAF_BODY"
```

The current F5 rejection page can return HTTP 200. Confirm the page title and a matching
[security event](../security-events/) with `action: "block"`; the status code alone is
not a WAF result. The generator sends the same bounded probe every fifth timer run.

**7. Check the generator timer on its dedicated VM.**

```bash
az vm run-command invoke \
  --resource-group rg-traffic-generator-lab-statistics \
  --name vm-traffic-generator-statistics \
  --command-id RunShellScript \
  --scripts 'systemctl is-active statistics-demo-traffic.timer; cat /var/lib/statistics-demo/run-count' \
  --query 'value[].message' --output tsv
```

Expect `active` and an increasing run count. The service sends at most three normal requests per minute and one WAF probe every fifth run.

**8. Record one [service graph](../service-graph/) sample after the first new five-minute bucket appears.**

**9. Wait for the next five-minute bucket.**

**10. Record a second service graph sample with a later timestamp and nonzero request rate.**

**11. Run each resource guide.**

**12. Check each response for the expected fields.**

**13. Record sanitized counts and times without tenant IDs, client addresses, headers, raw events, or credentials.**

The prototype observed one new service metric bucket about six minutes after a burst. Poll for up to ten minutes before treating absence as a failure.

## Verify request outcomes without stopping the origin

Capture baseline statistics before generating requests. The following sequence sends 30 requests sequentially: 20 health requests, five explicit 404 responses, and five explicit 503 responses. Each request has a ten-second timeout and a unique marker. It uses the origin's status routes, so the origin stays online. A status mismatch stops the sequence.

```bash
export XCSH_RUN_MARKER="statistics-outcomes-$(date -u +%Y%m%dT%H%M%SZ)"
export XCSH_BURST_START="$(date -u +%s)"
for XCSH_SEQUENCE in $(seq 1 30); do
  if [ "$XCSH_SEQUENCE" -le 20 ]; then
    XCSH_PATH=/health
    XCSH_EXPECTED=200
  elif [ "$XCSH_SEQUENCE" -le 25 ]; then
    XCSH_PATH=/httpbin/status/404
    XCSH_EXPECTED=404
  else
    XCSH_PATH=/httpbin/status/503
    XCSH_EXPECTED=503
  fi
  XCSH_STATUS="$(curl --silent --show-error --max-time 10 --output /dev/null \
    --write-out '%{http_code}' --get \
    --data-urlencode "statistics_probe=$XCSH_RUN_MARKER-$XCSH_SEQUENCE" \
    "https://$XCSH_DEMO_HOST$XCSH_PATH")"
  printf 'sequence=%s expected=%s status=%s\n' "$XCSH_SEQUENCE" "$XCSH_EXPECTED" "$XCSH_STATUS"
  test "$XCSH_STATUS" = "$XCSH_EXPECTED"
done
export XCSH_BURST_END="$(date -u +%s)"
```

The measured sequence ran from 2026-10-06T03:09:40Z to 2026-10-06T03:10:01Z. All 30 statuses matched: 20 × 200, five × 404, and five × 503. The existing timer continued to generate its normal traffic, so window-wide counts include background requests.

After rollup, refresh the shared query window and replay the guides. Keep receipts private with owner-only permissions,
including the UTC capture time, HTTP status, original response, request selector, and sanitized summary. Compare
published output to that summary; replace identifiers without changing measured values. Do not publish raw receipts,
headers, credentials, addresses, or captured bodies.

The first post-sequence log snapshot at 03:13:40 UTC counted 430 logs across five populated pages and an empty final
page. The complete window contained 413 responses with code 200, 12 with code 404, and five with code 503. The first
page contained 100 logs: 90 with code 200, five with code 404, and five with code 503. The discrepancy illustrates why
first-page class counts are not complete-window totals. All returned methods were GET.

The API-call summary from the same replay reported 378 calls, all in its returned 2xx class. Its top-active list covered three discovered endpoints. The explicit status routes were present in access logs but absent from that discovered-endpoint population. Compare these surfaces within their own scope rather than equating API calls with all HTTP requests.
