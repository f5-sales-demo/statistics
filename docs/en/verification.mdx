Verify that the demo serves requests, records WAF blocks, and returns telemetry. The measured results below show how access logs, API activity, and sampled metrics differ.

## Check readiness

For a new deployment, wait for the origin and generator applications to finish provisioning. Use the public routes as the application readiness check.

1. Check DNS and the HTTPS health route.

   ```bash
   dig +short "$XCSH_DEMO_HOST" A
   curl --silent --show-error --fail-with-body --output /dev/null \
     --write-out 'status=%{http_code} tls=%{ssl_verify_result}\n' \
     "https://$XCSH_DEMO_HOST/health"
   ```

   Expect `status=200 tls=0`, which confirms HTTP success and certificate verification.

2. Check an API route through the load balancer.

   ```bash
   curl --silent --show-error --fail-with-body --output /dev/null \
     --write-out 'status=%{http_code}\n' \
     "https://$XCSH_DEMO_HOST/httpbin/get?statistics_probe=$(date -u +%s)"
   ```

3. Check the WAF rejection page with one authorized probe to this F5-owned demo.

   ```bash
   XCSH_WAF_BODY="$(mktemp)"
   trap 'rm -f "$XCSH_WAF_BODY"' EXIT
   curl --silent --show-error --output "$XCSH_WAF_BODY" --write-out 'status=%{http_code}\n' \
     --get --data-urlencode "q=' OR 1=1--" \
     "https://$XCSH_DEMO_HOST/httpbin/get"
   grep -i '<title>Request Rejected</title>' "$XCSH_WAF_BODY"
   ```

   The rejection page can return HTTP 200. Confirm its title and a matching [security event](../security-events/) with `action: "block"`.

4. Check the generator timer on its dedicated VM.

   Authenticate to the approved Azure subscription before using the Azure CLI.

   ```bash
   az vm run-command invoke \
     --resource-group rg-traffic-generator-lab-statistics \
     --name vm-traffic-generator-statistics \
     --command-id RunShellScript \
     --scripts 'systemctl is-active statistics-demo-traffic.timer; cat /var/lib/statistics-demo/run-count' \
     --query 'value[].message' --output tsv
   ```

   Expect `active` and an increasing run count. The timer sends three normal requests each minute and one WAF probe every fifth run. Keep it enabled for fresh telemetry.

## Run the bounded request sequence

Record a baseline with [Load balancer metrics](../service-graph/). This sequence sends 30 requests: 20 health requests, five explicit 404 responses, and five explicit 503 responses. Each request has a ten-second timeout and a unique marker. The origin stays online. A status mismatch stops the sequence.

```bash
export XCSH_RUN_MARKER="statistics-outcomes-$(date -u +%Y%m%dT%H%M%SZ)"
export XCSH_BURST_START="$(date -u +%s)"
for XCSH_SEQUENCE in $(seq 1 30); do
  if [ "$XCSH_SEQUENCE" -le 20 ]; then
    XCSH_PATH=/health
    XCSH_EXPECTED=200
  elif [ "$XCSH_SEQUENCE" -le 25 ]; then
    XCSH_PATH=/httpbin/status/404
    XCSH_EXPECTED=404
  else
    XCSH_PATH=/httpbin/status/503
    XCSH_EXPECTED=503
  fi
  XCSH_STATUS="$(curl --silent --show-error --max-time 10 --output /dev/null \
    --write-out '%{http_code}' --get \
    --data-urlencode "statistics_probe=$XCSH_RUN_MARKER-$XCSH_SEQUENCE" \
    "https://$XCSH_DEMO_HOST$XCSH_PATH")"
  printf 'sequence=%s expected=%s status=%s\n' "$XCSH_SEQUENCE" "$XCSH_EXPECTED" "$XCSH_STATUS"
  test "$XCSH_STATUS" = "$XCSH_EXPECTED"
done
export XCSH_BURST_END="$(date -u +%s)"
```

After telemetry rollup, [refresh the query window](../setup/#refresh-the-time-window) and compare [HTTP access logs](../access-logs/#count-all-matching-logs), [API activity](../api-discovery/), and load balancer metrics. Allow up to ten minutes for a new five-minute metric bucket.
